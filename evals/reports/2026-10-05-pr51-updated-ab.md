## Error analysis (all three failed transcripts read)

| First failure | Trials | Evidence and interpretation |
|---|---:|---|
| Ambiguous confirmation paths use separate counters | 2 | `dispute-unclear-replies-handoff-es`, trials 0 and 1: “lo reconozco” and “ese mismo” return to search and re-propose the same transaction; “claro que sí” takes the affirmative-but-not-explicit path and repeats the card. `_phase_confirm_dispute` increments `unclear_detours` on free-text detours, but `_unclear_reply` increments `unclear_count` on affirmative non-consent. The three ambiguous replies never reach one shared limit. The next simulated “no” rejects the transaction rather than answering the expected offer of a person. No unauthorized action occurred. This is an orchestration regression covered by an existing dev case. |
| Found transaction, asked a question the simulator cannot answer | 1 | `dispute-flex-merchant-misspelled-es`, trial 1: queries correct “Starbuks” to “Starbucks”, find the target, then ask “¿Qué monto esperabas que te cobraran?” rather than calling `propose_transaction`. The reactive customer has no informative turn for that question, so the trial ends in clarify. This is an interaction/simulator limitation as well as a failure to reach the prescribed proposal flow; it is not a lookup failure. Keep the failed grade, but do not infer inability to resolve with a real customer. |

Prioritized follow-ups:
1. Count all ambiguous confirmation replies toward one shared bounded limit, including detours and
   affirmative non-consent. Validate the existing unclear-replies case with the real classifier.
2. Cover legitimate follow-up questions with a customer simulator that can answer from known facts, or
   make the proposal goal clearer. Do not relabel this failure as a pass without a new, documented run.
3. Classify budget exhaustion as an infrastructure/configuration error in the runner, rather than a failed
   product outcome. Add a deterministic regression case to the harness tests before fixing it.

Existing dev cases expose the first two paths; no test cases were edited or generated in the locked split.
No fixes were applied during this A/B.

## Discarded attempt and budget accounting

The initial workflow attempt used 37 cases × 3 trials and a USD 0.40 cap. Although its upfront estimate was
USD 0.3593832, real reservations exceeded the cap before completion. It finished as 78/111 passed, with
33 subsequent 503 contract failures and no infrastructure exclusions. Inspection shows budget exhaustion
was handled as service unavailability, not a model quality regression. That run is excluded from the A/B:
`evals/runs/pr51-updated-workflow-56e1c86`. Recorded usage USD 0.0328348; reservation USD 0.3998389.

The pair was rerun with **two**, not three, trials per case to stay within the user's approved USD 7.50.
Run caps, including the discarded attempt, sum to USD 5.80. Total recorded usage across all three runs:
**USD 0.1138290**; total reservations: **USD 1.3441834**. The older budget ledger is unchanged;
this separately authorized batch has its own ledger. Prior unaccounted runs are not reconciled here.

## Merge implication

This supplies a current live dev comparison, not evidence to switch the default to agentic. Keep workflow
as default. The ambiguous-confirmation regression should be fixed and re-evaluated before calling the
agentic option ready for adoption; the architectural ADR and review remain separate requirements.
